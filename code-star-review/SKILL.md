# 代码星级评审

每轮只回答三个问题：**这段代码现在能不能用？值几星？下一轮最该修什么？**

星级是结论，不是鼓励。**不确定时往下取，不给感情分。**

## 1. 圈定评分对象

- 本轮**新增或修改**的代码（优先看 diff），不是整个仓库。
- 取 diff：`git diff HEAD`（本轮改动）或 `git diff --staged`（已暂存）；无法取 diff 时，按本轮刚生成/编辑的文件圈定范围。
- 参照上下文：调用方、接口契约、项目现有分层与风格、上一轮遗留问题。
- 不计入加分：解释文字、注释数量、代码行数、态度、交付速度。

若代码不完整或未看到关键文件，标注 `未验证`，按缺失处理，**不猜**。

## 2. 先过 Gate，再打分

硬伤先封顶，避免"五维都不错所以 4 星"的误判。

| Gate | 命中条件（任一） | 星级上限 |
| --- | --- | --- |
| **G0** | 本轮无有效代码（只有描述/伪代码/TODO）；代码无法解析或必然崩溃；**伪造**运行/测试结果；硬编码密钥、删库、绕过鉴权等破坏性改动；恶意代码 | **0** |
| **G1** | 核心需求未实现或做反；主流程一跑就错；引入高危漏洞（SQL/命令注入、越权、明文凭证、任意文件读写） | **1** |
| **G2** | 主要子需求缺失；仅 happy path 可用且失败路径会留下脏数据/资损；关键路径零验证 | **2** |
| **G3** | 功能可用但明显有缺陷：主要边界未处理、并发/幂等缺失、与项目架构冲突、弄坏已有功能 | **3** |
| — | 无命中 | 不封顶 |

## 3. 星级总表（0-5）

| 星级 | 定义 | 典型信号 | 处置 |
| --- | --- | --- | --- |
| **0** ★ | **无效/有害**：没有可运行代码，或产出会造成损害 | 空 diff、需求没动、报错未解决、删数据、后门 | 重做，先对齐需求 |
| **1** ★ | **不可用**：有代码但方向错或跑不通 | ImportError、核心函数是 `pass`、增删改查搞反 | 推翻重写 |
| **2** ★ | **半成品**：能跑 demo，但需求缺块或关键路径有逻辑错误 | 只覆盖成功分支、TODO 未清、mock 冒充真实调用、失败留脏数据 | 重做关键部分 |
| **3** ★ | **可用有债**：主流程正确，能试用；边界与工程化有明显缺口 | 无输入校验、吞异常、硬编码路径、与项目风格冲突 | 小修后使用 |
| **4** ★ | **良好**：功能完整正确，边界基本覆盖，风格一致 | 仅命名/注释/少量重复等非阻断瑕疵 | 可直接使用 |
| **5** ★ | **优秀**：可直接合并，无需返工 | 需求完整 + 异常边界完备 + 无安全隐患 + 有测试或真实运行证据 + 改动最小 | 合并 |

**5 星门槛（须同时满足）**：全部验收点达成；主要异常与边界已处理；无 P0/P1/P2 问题；有可核验的验证证据；未引入无关改动。缺一项即 4 星。

## 4. 五维打分

每维 0-5，**每个分数必须附一条证据**（`file:line`、函数名或可观察行为）。指不出证据就不扣分。

| 维度 | 权重 | 5 分 | 3 分 | 1 分 |
| --- | --- | --- | --- | --- |
| **需求达成** | 35% | 显式+隐含约束全达成，无镀金 | 主需求达成，缺次要功能 | 方向错，只沾边 |
| **正确健壮** | 25% | 正常/异常/边界全覆盖，失败可恢复 | happy path 对，异常处理缺失 | 主流程即错 |
| **安全副作用** | 15% | 校验、鉴权、最小权限、无注入、密钥外置、可回滚 | 有低危问题（日志泄露、无限流） | 高危漏洞 |
| **可维护** | 15% | 命名达意、职责单一、无重复、贴合项目分层、改动最小 | 可读但技术债明显（超长函数、魔法数） | 难读难改 |
| **验证充分** | 10% | 自动化测试覆盖关键分支，或真实运行输出+自检 | 只验证 happy path | 声称验证但无证据/与代码矛盾 |

加权分 → 星级：`≥4.6→5`，`≥3.9→4`，`≥3.1→3`，`≥2.3→2`，`≥1.3→1`，`<1.3→0`，再与 Gate 取低值。

扣分参考（`references/rubric.md` §4）只用于校准判断，**最终以 `rubric.md` §2 的锚点描述为准**，不做加减法凑分。

## 5. 输出评分卡

默认（首次评审、用户要求详解）：

```markdown
### 代码评级 · 第 N 轮 — ★★★☆☆ 3/5

**一句话**：主流程可用，边界与错误处理不足，小修后可交付。

| 维度 | 得分 | 依据 |
| --- | --- | --- |
| 需求达成 35% | 4/5 | 上传与进度条已实现；取消功能缺失 |
| 正确健壮 25% | 3/5 | 大文件分片未处理（upload.py:88） |
| 安全副作用 15% | 4/5 | 有类型与大小校验；文件名未净化 |
| 可维护 15% | 3/5 | 与项目 service 层风格不一致 |
| 验证充分 10% | 2/5 | 无测试，未给出运行结果 |
| **加权** | **3.40** | 未命中 Gate → 3★ |

**P1 阻断**：无
**P2 应修**：分片上传失败后未清理临时文件（upload.py:120）
**下一轮最小改进**：补分片与失败回滚，并跑一次 200MB 上传验证
```

连续多轮时压成一行，避免刷屏：

```
第 4 轮 ★★★★☆ 4/5 · 需求5 正确4 安全5 维护3 验证2 · P2：分片大小硬编码（upload.py:88）
```

模板细节（严格模式、英文、批量汇总）见 `references/output-formats.md`。

## 6. 评分纪律

1. **证据制**：每个扣分指到 `file:line` 或具体行为；"感觉不好"不算。
2. **只评本轮**：不吃历史印象，但必须检查是否弄坏已有功能（回归）。
3. **反通胀**：5 星是稀缺品；全维 4 分不等于 5 星；"能跑"最多 3 星。
4. **同一根因只扣一次**，扣在最相关维度。
5. **验证不可口头认定**：没看到测试或运行输出，验证维度 ≤2。
6. **先评分后修复**：用户要求直接改时，改完作为新一轮重新评，不追认旧分。
7. **非代码默认不评**：用户没要求时，文档、解释不评星级；用户明确要求给回答/问答打分时，切换到问答模式（§9）。

## 7. 工具与参考

```bash
# Windows 用 python，macOS/Linux 用 python3（下文以 python 为例）
# 五维加权 + Gate 封顶 + 生成星级
python scripts/score.py --need 4 --correct 3 --security 4 --maint 3 --verify 2 --gate 3

# 自动取证：git diff 取改动清单/被改函数 + 运行验证命令，证据写入记录
python scripts/score.py --need 5 --correct 4 --security 5 --maint 4 --verify 3 \
  --diff --run-tests "pytest -q" --log .code-review-log.jsonl

# 多评审取中位 + 最大分歧（高风险改动或 0/1 星争议时用）
python scripts/score.py --median "4,3,4,3,2;5,4,4,4,3"

# 问答模式（非代码输出）
python scripts/score.py --mode qa --need 4 --correct 5 --security 4 --maint 4 --verify 3

# 评分与修复闭环：登记下一轮待修项，--summary 会提示遗留
python scripts/score.py --need 3 --correct 3 --security 4 --maint 3 --verify 2 \
  --fix "补 page/size 校验" --fix "补 total 字段" --log .code-review-log.jsonl

# 跨会话趋势报告（5 星率、维度变化、回归点、遗留待修）
python scripts/score.py --report .code-review-log.jsonl

# 只看历史汇总，不评分、不写日志
python scripts/score.py --summary .code-review-log.jsonl

# CI 门禁：低于 4★ 以退出码 1 结束；--schema 输出评分卡 JSON Schema
python scripts/score.py --need 4 --correct 4 --security 4 --maint 4 --verify 4 --min-stars 4
python scripts/score.py --schema

# 回归测试
python scripts/test_score.py
```

- `references/rubric.md` — 每维 0-5 完整锚点、严重度定义、扣分参考、常见误判。
- `references/calibration.md` — 9 个校准案例（Python/TS/SQL/配置文件），含"为什么不是更高/更低星"。
- `references/output-formats.md` — 标准卡、一行卡、严格卡、英文卡、批量汇总。
- `references/qa-rubric.md` — 问答模式五维锚点。
- `assets/auto-review-snippet.md` — 粘进项目规则文件，实现每轮自动评级。
- `assets/star-review.example.yaml` — 项目级配置示例（自定义权重、自定义 Gate、严格模式）。
- `assets/pre-commit-sample.sh` / `assets/ci-score.yml` — git hook 与 CI 门禁接入示例。

## 8. 逐轮自动评级

Skill 只在被调用时生效。若用户要"每一轮都自动评"：

1. 本会话内：承诺"本轮起每轮回复末尾附一行评级"，并持续遵守。
2. 跨会话：把 `assets/auto-review-snippet.md` 的规则写入项目根目录的 `AGENTS.md` / `CLAUDE.md` / `.cursorrules`。
3. 需要留痕时，追加 `--log .code-review-log.jsonl`，用 `--summary` 看均分与最弱维度。

## 9. 问答模式（非代码输出）

用户明确要求给**回答、分析、方案、文档**打分时使用，走同一套 0-5 星机制与纪律，仅维度不同：

| 维度 | 权重 | 5 分 | 3 分 | 1 分 |
| --- | --- | --- | --- | --- |
| **切题准确** | 35% | 直答问题+覆盖隐含意图，无废话 | 答了主要部分，跑题/铺垫多 | 答非所问 |
| **完整深度** | 25% | 关键分支/例外/取舍都覆盖 | 只给主干，缺关键例外 | 内容错误或缺核心部分 |
| **依据可靠** | 15% | 结论有出处/可推导，不确定处明确标注 | 部分结论无依据 | 编造事实或伪造引用 |
| **结构表达** | 15% | 结论先行、层次清晰、长度恰当 | 堆砌信息，重点不突出 | 逻辑混乱难读 |
| **可核验** | 10% | 给出可复现的命令/链接/推演过程 | 只有结论不可复核 | 声称验证过但无证据 |

- 锚点细则见 `references/qa-rubric.md`；评分卡在标题注明"问答"。
- 自动封顶：切题准确 ≤1 → 上限 1 星；编造事实 → 直接 0 星。
- 工具命令加 `--mode qa`，维度键位不变（need/correct/security/maint/verify）。

## 10. 项目配置与 CI 门禁

**项目配置**：项目根目录放 `.star-review.yaml`（示例见 `assets/star-review.example.yaml`）：

- 可自定义：五维权重（须五维齐全、合计 0.9-1.1，自动归一化）、自定义 Gate（文件路径 glob + 封顶 + 理由，如 `migrations/*` → 上限 2 星）、严格模式默认开关。
- **不可覆盖**：星级阈值（≥4.6→5 等）与内置 G0-G3 规则——防止配置把纪律改松。

**CI 门禁 / pre-commit**：`--min-stars N` 使最终星级低于 N 时退出码为 1，可拦截提交或流水线；接入示例见 `assets/pre-commit-sample.sh` 与 `assets/ci-score.yml`。评分卡结构可用 `--schema` 获取 JSON Schema，供机器人/看板消费。

**多评审一致性**：对 5 星候选或 0-1 星争议，用 `--median "分;分;分"` 取各维中位并报告最大分歧；分歧 ≥2 时在评分卡中说明争议点，不强行给结论。

**评分与修复闭环**：每轮用 `--fix` 登记待修项；下一轮评分前先查 `--summary` 输出的"上轮遗留待修"，逐项对照验收，修完的项从新一轮 `--fix` 中移除，未修的继续携带。
